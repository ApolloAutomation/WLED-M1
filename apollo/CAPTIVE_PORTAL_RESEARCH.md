# Can the captive popup coexist with full AP functionality? (researched 2026-07-15)

Verdict: NOT on stock Android without at least one user tap - the wall is
cryptographic (validation requires an HTTPS probe the device cannot serve).
Raw research with sources below, three tracks.

## Track A: hotel two-phase pattern

RAW FINDINGS — Two-phase captive portal ("hotel-login pattern": 302 first, then 204) on Android and iOS

=== BOTTOM LINE ===
The pattern is architecturally supported — it is literally the flow Android and iOS were designed around for real hotel portals, and both OSes re-probe after portal interaction and promote the network when probes flip to success. BUT on stock Android 10+ there is one hard blocker for an offline AP: full VALIDATED status normally requires the **HTTPS** probe (https://www.google.com/generate_204) to succeed, which an ESP32 with no internet and no valid Google cert cannot serve. HTTP-only 204 yields PARTIAL connectivity, which does not silently become the default route — it needs one user tap. iOS has no such blocker (probes are plain HTTP). Details below.

=== TASK A1: Android — does the network become VALIDATED + default after probes flip to 204? ===
- Official flow (Android docs for ACTION_CAPTIVE_PORTAL_SIGN_IN): after the portal app "believes the user has signed in... the app should call CaptivePortal#reportCaptivePortalDismissed so the system can reevaluate the network. If reevaluation finds the network no longer subject to a captive portal, the network may become the default active data network." (https://learn.microsoft.com/en-us/dotnet/api/android.net.connectivitymanager.actioncaptiveportalsignin?view=net-android-35.0 — mirror of the Android Javadoc)
- Android 11 captive-portal API docs confirm capability transitions: while portal-captive, network has NET_CAPABILITY_INTERNET + NET_CAPABILITY_CAPTIVE_PORTAL but NOT NET_CAPABILITY_VALIDATED; after login it "gains the NET_CAPABILITY_VALIDATED capability and loses NET_CAPABILITY_CAPTIVE_PORTAL" (https://developer.android.com/about/versions/11/features/captive-portal).
- CRITICAL CAVEAT (verified in AOSP NetworkMonitor, android10-dev branch, packages/modules/NetworkStack): HTTP and HTTPS probes run in parallel (`sendParallelHttpProbes`). Code: `if (httpsProbe.result().isFailed() && isHttpSuccessful) { return CaptivePortalProbeResult.PARTIAL; }` — i.e., HTTP 204 + failed HTTPS = PARTIAL connectivity, not VALID. Full validation from probes alone requires the HTTPS probe to succeed, or `captive_portal_use_https=0` (a Settings.Global knob, not device default). (https://android.googlesource.com/platform/packages/modules/NetworkStack/+/refs/heads/android10-dev/src/com/android/server/connectivity/NetworkMonitor.java)
- PARTIAL produces the "this network has limited connectivity — tap to connect anyway" notification; only after the user accepts does NetworkMonitor disable HTTPS probing and report VALID (then Wi-Fi can become default). So on stock Android 10-16, the 204-flip alone gets you to a one-tap prompt, not silently to default-route.
- Escape hatch that DOES fully validate without HTTPS: the sign-in webview's overflow menu "Use this network as is" → `mCaptivePortal.useNetwork()` → APP_RETURN_WANTED_AS_IS → NetworkMonitor immediately does `mEvaluationState.reportEvaluationResult(NETWORK_VALIDATION_RESULT_VALID, null)` and disables HTTPS probes (verified in current NetworkMonitor.java, https://android.googlesource.com/platform/packages/modules/NetworkStack/+/refs/heads/main/src/com/android/server/connectivity/NetworkMonitor.java).
- Note the tension with the reported empirical result ("204-always validates and browsers work with mobile data on"): that is consistent with (a) OEM stacks (e.g., Samsung uses its own single HTTP probe and hardcoded 8.8.8.8 DNS — foxblock/esp-captive-portal README, https://github.com/foxblock/esp-captive-portal), (b) the user having previously accepted the partial-connectivity prompt (per-network setting persists), or (c) older Android. Needs per-device testing; do not assume HTTP-204 = VALIDATED on stock Pixels.
- Default-network ranking: selection is NetworkRanker/NetworkScore-based; validation is a scoring input, and validated Wi-Fi is preferred over cellular (https://source.android.com/docs/core/connect/network-selection, https://source.android.com/docs/core/connect/wifi-network-selection).
- Private DNS (DoT strict mode) breaks the whole scheme — validation includes a private-DNS phase (EvaluatingPrivateDnsState) that an offline AP can't satisfy.

=== TASK A2: What triggers Android's re-probe ===
Verified triggers (AOSP sources above + CaptivePortalLoginActivity):
1. Every page navigation inside the sign-in webview: modern CaptivePortalLoginActivity calls `mCaptivePortal.reevaluateNetwork()` in both onPageStarted() and onPageFinished() (https://android.googlesource.com/platform/packages/modules/CaptivePortalLogin/+/refs/heads/master/src/com/android/captiveportallogin/CaptivePortalLoginActivity.java). Older (API 27) versions ran their own HTTP GET of the probe URL after each page load; `isDismissed()` = `httpResponseCode == 204` → `done(Result.DISMISSED)` → `reportCaptivePortalDismissed()` (https://github.com/elastic/AndroidSDKMirror-27/blob/master/com/android/captiveportallogin/CaptivePortalLoginActivity.java).
2. reportCaptivePortalDismissed → NetworkMonitor CMD_CAPTIVE_PORTAL_APP_FINISHED / APP_RETURN_DISMISSED → `sendMessage(CMD_FORCE_REEVALUATION)` → immediate full re-probe.
3. Periodic recheck while in CaptivePortalState: `CAPTIVE_PORTAL_REEVALUATE_DELAY_MS = 10 * 60 * 1000` — every 10 minutes while the "Sign in to network" notification shows. So even a user who never opens the popup gets re-probed within 10 min of the flip.
4. Apps calling ConnectivityManager.reportNetworkConnectivity / capability changes also force reevaluation.
Practical implication: after flipping to 204, the popup self-dismisses on its next page navigation (or the periodic probe), then the immediate re-probe runs — landing on PARTIAL (see A1) on stock modern Android.

=== TASK A3: iOS CNA ===
- Probes: http://captive.apple.com/hotspot-detect.html (User-Agent "CaptiveNetworkSupport... wispr"), expecting an HTML page containing "Success". Redirect/other content → CNA sheet opens.
- After login, the CNA mini-browser (CPMB) re-checks the probe on every FULL page navigation ("a javascript-triggered AJAX call... will not result in the CPMB performing an additional check"). When the probe finally returns Success, the button flips from "Cancel" to "Done" AND iOS "switches the primary connection from cellular network to Wi-Fi." (Wireless Broadband Alliance captive-portal behavior reference: https://captivebehavior.wballiance.com/)
- So the two-phase pattern works cleanly on iOS: serve the portal page to the CNA, flip probes to Success after the user's action, make sure the action ends in a real page navigation, user taps Done, Wi-Fi becomes primary. No HTTPS-probe problem — Apple's probe is plain HTTP.
- Failure modes: tapping Cancel disassociates the device from the Wi-Fi network entirely; iOS also offers "Use Without Internet" (keeps association, disables auto-login for that network) (https://support.apple.com/en-us/102554, https://captivebehavior.wballiance.com/). CNA mini-browser is feature-limited (no real browser chrome; cookies/JS quirks — https://medium.com/@rwbutler/solving-the-captive-portal-problem-on-ios-9a53ba2b381e).

=== TASK A4: IoT/ESP32 precedent for two-phase probe strategy ===
- No named ESP32/ESP8266 project found that implements 302-first-then-204. The ecosystem is split into two static camps: always-302 (popup; WiFiManager, ESPHome captive_portal, most tutorials) vs always-204 (suppress popup so the user's real browser works; e.g., discussion in tzapu/WiFiManager issue #114, where the 204 handler was debated precisely because it forces manual browsing but keeps the network usable — https://github.com/tzapu/WiFiManager/issues/114; also an esp32.com thread "Landing Page for IoT application / Avoid captive portal" where a dev serves 204 on all three OSes to avoid the banner — https://esp32.com/viewtopic.php?p=143179&t=44005).
- Related but not identical: Foxdog Studios "Making Phones Believe the WiFi has Internet" (offline AP answering all Android generate_204 endpoints with 204 and Apple probes with Success pages; notes Google-cert risk of impersonating www.google.com over HTTPS) — https://foxdogstudios.com/blog/making-phones-believe-the-wifi-has-internet/
- Multi-probe handling references: Nordesems/esp-captive-portal (11 probe endpoints, 302+meta-refresh+JS fallback, /generate204 variant to stop 404 retry storms) https://github.com/Nordesems/esp-captive-portal; foxblock/esp-captive-portal (Samsung hardcoded-8.8.8.8 workaround: set AP IP to 8.8.8.8) https://github.com/foxblock/esp-captive-portal; CDFER/Captive-Portal-ESP32 (device test matrix; notes a OnePlus DHCP hang unless cellular is off; macOS Big Sur+ no popup) https://github.com/CDFER/Captive-Portal-ESP32.
- ESPHome deliberately treats the captive portal as a fallback and pushes Improv BLE/Serial because portal behavior across OSes is unreliable (https://esphome.io/components/captive_portal/, https://www.improv-wifi.com/, https://deepwiki.com/esphome/esphome/9.2-device-provisioning-(improv-and-captive-portal)). The hotel pattern itself is standard infrastructure behavior, so OS support is by design — the novelty here is only doing it on an AP that never gets real internet, which is exactly what trips the Android HTTPS-probe requirement.

=== TASK A5: Failure modes if the user ignores/dismisses the popup ===
- Ignore entirely: Android stays associated; network stays in CaptivePortalState, unvalidated; cellular remains default; persistent "Sign in to network" notification; periodic re-probe every 10 min (so with the flip, the network self-advances to PARTIAL + "tap to connect anyway" prompt without the popup ever being opened). Android does not tear the network down for mere inaction.
- Back-press out of the sign-in webview: activity just finishes (`super.onBackPressed()`); no `ignoreNetwork()` call, so no penalty — network remains connected/unvalidated (verified in API-27 source above).
- Explicit "Don't use this network": `mCaptivePortal.ignoreNetwork()` → APP_RETURN_UNWANTED → `mUserDoesNotWant = true`, evaluation reported invalid — the network will not validate for the rest of the session; user must reconnect.
- Auto-reconnect to known captive-portal networks that were never signed in can be disabled by the platform (Google issue tracker 37032027, "Wifi automatic reconnection disabled for captive portals" — page requires login, content unverified).
- iOS: Cancel = full disassociation from the AP (worst failure mode — user must rejoin); "Use Without Internet" keeps the connection and, since iOS keeps Wi-Fi usable in that state, a real Safari can then reach 4.3.2.1 (iOS does not have Android's per-app cellular-default problem to the same degree).
- Cross-cutting: Private DNS strict mode and per-network MAC randomization can break detection/flip tracking (track clients by IP/lease, not across reconnects); Samsung's hardcoded-DNS probe bypasses DNS spoofing unless AP IP is 8.8.8.8.

=== DESIGN IMPLICATIONS FOR THE 4.3.2.1 DEVICE ===
1. iOS: two-phase works as designed. Flip probes to "Success" per-client after the user completes (or explicitly skips) setup in the CNA; ensure the flip is followed by a full page navigation so the CNA re-checks and shows Done; iOS then makes Wi-Fi primary. Never let users hit Cancel without warning (it disconnects them).
2. Android: two-phase gets popup + auto-dismiss + immediate re-probe, but on stock Android 10+ the re-probe result is PARTIAL (HTTPS probe unanswerable offline) → user must tap the "limited connectivity / connect anyway" notification once, or pick "Use this network as is" in the popup's menu, before Wi-Fi becomes the default route for Chrome. Consider putting an instruction in the portal page ("tap the connectivity notification / use-network-as-is") — or test whether target OEM builds (Samsung et al.) validate on HTTP alone.
3. Flip granularity must be per-client (per IP/MAC), or one phone's dismissal kills the popup for the next phone that joins.
4. The 10-minute CaptivePortalState recheck is a free retry channel: even users who swipe the popup away converge to the PARTIAL prompt after the flip.

## Track B: RFC 8908/8910 capport API

RAW FINDINGS — TASK B: RFC 8908/8910 (ex-7710) Captive Portal API + venue-info-url

## 1. Real-world client support (as of 2026)

**Android:**
- Android 11+ parses DHCP option 114 (RFC 8910) and fetches the RFC 8908 API "immediately after connecting," per [Android 11 captive portal API docs](https://developer.android.com/about/versions/11/features/captive-portal). RA (IPv6) option support was "may be added in a future update" at launch — DHCP is the reliable path.
- What Android does with `venue-info-url`: shows a **home-screen notification** the user can tap, plus an **"Open Site"-style entry in the Network details screen** ([Android docs](https://developer.android.com/about/versions/11/features/captive-portal); [stevetech.me write-up](https://stevetech.me/posts/wifi-captive-portal-api) — that post is specifically about adding `captive:false` + `venue-info-url` to a *home* (non-captive) network and shows Android surfacing "Open Site" in Wi-Fi settings and a notification shortcut; a [UniFi community thread](https://community.ui.com/questions/Capport-API-Venue-Info-URL-works-amazing-on-Android-12/3b1fd283-d522-4dfc-b30c-6f97e85bd089) reports the same "works amazing on Android 12"). `seconds-remaining` shows in Settings; expiry is informational only.
- Crucially, per Android's own docs, capport data is **supplementary to, not a replacement for, probe-based validation**: if the API says `captive:false`, the system still runs its normal HTTP/HTTPS probes to decide validation; if the API is unavailable or its cert is bad, it silently **falls back to legacy probe behavior** ([Android docs](https://developer.android.com/about/versions/11/features/captive-portal)). So option 114 never *breaks* anything — it just gets ignored on failure.

**iOS/macOS:**
- iOS 14+ / macOS Big Sur+ fetch option 114 per [Apple's "How to modernize your captive network"](https://developer.apple.com/news/?id=q78sq5rv). Confirmed fetching in the field (pfSense logs show iPhones GET-ing the RFC 8910 URL: [Netgate forum thread](https://forum.netgate.com/topic/188402/captive-portal-not-working-on-ios-devices-only-dhcp-114/20)).
- **iOS does essentially nothing user-visible with `venue-info-url`.** An [Apple Developer Forums thread](https://developer.apple.com/forums/thread/695574) (no Apple response) reports iOS 15.7 shows no notification — only the CNA sheet when `captive:true`; follow-up reports say **still no venue notification as of iOS 17**. At best it's a link buried in the Wi-Fi network's detail page ([splashnetworks MikroTik writeup](https://blog.splashnetworks.co/captive-portal-api-and-venue-info-url-on-mikrotik/) describes a "Portal" section in Wi-Fi settings). [hgot07's VenueInfoHandler](https://github.com/hgot07/VenueInfoHandler) (Tohoku Univ. public-Wi-Fi project, extensive real testing: Android 11+, iOS/iPadOS 15+, macOS 13+) explicitly works around this: on Apple OSs he *forces* `captive:true` "since they haven't got a nice notification mechanism."
- iOS quirk: option 114 handling is "sticky" per network; stale entries can require forgetting the network ([Netgate](https://forum.netgate.com/topic/188402/captive-portal-not-working-on-ios-devices-only-dhcp-114/20), [OpenWrt thread](https://forum.openwrt.org/t/dhcp-option-114-and-160-for-captive-portal/148764)).
- Windows 10/11 and most Linux ignore option 114 and keep using their own probes ([systemd issue #25517](https://github.com/systemd/systemd/issues/25517) — still an open request for Linux).

**The TLS wall (applies to everything above):** [RFC 8908 §4/§4.1](https://datatracker.ietf.org/doc/html/rfc8908): API "MUST be accessed over HTTP using an https URI"; client must validate a DNS-ID matching the provisioned hostname, with revocation checks; "If the client is unable to validate the certificate… it MUST NOT proceed with any of the behavior for API interaction." Apple's doc repeats the TLS requirement. Field-confirmed on pfSense: iPhones and Android 11+ rejected the capport API until a real public-DNS hostname + CA-issued cert with matching SAN was in place ([Netgate thread](https://forum.netgate.com/topic/188402/captive-portal-not-working-on-ios-devices-only-dhcp-114/20)). An option-114 URL like `http://4.3.2.1/api` or a self-signed HTTPS cert is discarded and the phone reverts to probe behavior. An offline ESP32 cannot satisfy this: it would need a publicly trusted cert (impossible for a bare IP; a real domain would require shipping the private key in firmware and renewing every ~90 days with no internet). This is the decisive blocker.

## 2. ESP32: can the softAP DHCP server emit option 114?

Verified directly in ESP-IDF source (downloaded and grepped both trees):

- **ESP-IDF 4.4 / arduino-esp32 2.x: NO.** `components/lwip/apps/dhcpserver/dhcpserver.c` at v4.4.7 contains zero option-114/captive-portal code, and `dhcps_set_option_info()` accepts only 5 hardcoded options: `IP_ADDRESS_LEASE_TIME`, `REQUESTED_IP_ADDRESS`, `ROUTER_SOLICITATION_ADDRESS`, `DOMAIN_NAME_SERVER`, `SUBNET_MASK`. No generic custom-option API, and no lwIP hooks in the 4.4 dhcpserver. The only routes on 2.x are: (a) patch dhcpserver.c and rebuild the precompiled Arduino libs via esp32-arduino-lib-builder, or (b) stop the built-in dhcps and run a hand-rolled DHCP server on a raw UDP:67 socket. Original feature request dates to 2018 ([esp-idf #2723, IDFGH-465](https://github.com/espressif/esp-idf/issues/2723)).
- **ESP-IDF 5.4+: YES, natively.** Confirmed in source: `DHCP_OPTION_CAPTIVEPORTAL_URI 114` in dhcpserver.c, `ESP_NETIF_CAPTIVEPORTAL_URI = 114` in [esp_netif_types.h](https://github.com/espressif/esp-idf/blob/master/components/esp_netif/include/esp_netif_types.h), set via `esp_netif_dhcps_option(netif, ESP_NETIF_OP_SET, ESP_NETIF_CAPTIVEPORTAL_URI, uri, strlen(uri))` (server stopped/restarted around the call) — used by the official [captive_portal example](https://github.com/espressif/esp-idf/blob/master/examples/protocols/http_server/captive_portal/main/main.c). I grepped tags v5.0.7/v5.1.4/v5.2.3/v5.3.1 — **absent in all**; first appears in v5.4. Master also gained a `LWIP_HOOK_DHCPS_POST_APPEND_OPTS` compile-time hook for arbitrary options (still requires rebuilding lwIP, so not usable from stock Arduino cores).
- **arduino-esp32:** available once the core moved to IDF 5.4; PR [#11412](https://github.com/espressif/arduino-esp32/pull/11412) (merged June 2025, milestone 3.3.0) adds a first-class `WiFi.AP.enableDhcpCaptivePortal()` API; on 3.2.x you can call `esp_netif_dhcps_option()` directly. Tracking issue: [arduino-esp32 #11399](https://github.com/espressif/arduino-esp32/issues/11399).
- Real-world result on ESP32 anyway: an [esp32.com thread](https://esp32.com/viewtopic.php?t=42046) titled "Captive portal using DHCP option 114 not working on Android/iOS" matches the TLS analysis — phones fetch the URL but discard it without a valid HTTPS endpoint.

## 3. Does {captive:false, venue-info-url} give BOTH validation and a prompt?

**Conceptually on Android 11+: yes, that's exactly the designed combo** — the capport API returning `captive:false` never marks the network captive, Android proceeds to normal probe validation (your existing 204-spoof still required — the API result does not itself validate the network), and `venue-info-url` yields a tappable notification + Wi-Fi-details "Open Site" button that opens in the **regular browser over the (validated) Wi-Fi**, which is precisely the "both" outcome ([Android docs](https://developer.android.com/about/versions/11/features/captive-portal), [stevetech.me](https://stevetech.me/posts/wifi-captive-portal-api), [UniFi thread](https://community.ui.com/questions/Capport-API-Venue-Info-URL-works-amazing-on-Android-12/3b1fd283-d522-4dfc-b30c-6f97e85bd089)).

**Practically for this product: no.**
1. The API endpoint must be HTTPS with a publicly-trusted, hostname-matching, revocation-checkable cert (RFC 8908 §4.1 MUST; enforced by Android and iOS per the pfSense evidence). An offline ESP32 at 4.3.2.1 cannot present one; the phones then silently ignore option 114 and you're back to plain probe behavior — no venue notification, no harm either.
2. Even with valid TLS, **iOS gives no prompt for venue-info-url** (nothing as of iOS 17; hgot07 resorts to forcing `captive:true` on Apple devices). So "both" would be Android-only.
3. Windows/Linux ignore the mechanism entirely.

Side note: RFC 8910 defines the special option-114 value `urn:ietf:params:capport:unrestricted` ("no portal here") which needs no API server and no TLS — seen working in DHCP captures ([OpenWrt thread](https://forum.openwrt.org/t/dhcp-option-114-and-160-for-captive-portal/148764)) — but it only suppresses captive handling; it produces no user-visible prompt and does not validate the network, so it doesn't achieve "both" either.

**Bottom line for the orchestrator:** RFC 8908 capport is the standards-blessed way to get validation + prompt, and the ESP32 side is now trivially implementable (IDF 5.4+ / arduino-esp32 3.2+/3.3, one API call; impossible on stock IDF 4.4/arduino 2.x without patching lwIP or a custom UDP DHCP server). But the mandatory publicly-trusted-TLS requirement makes it unusable on an offline device at 4.3.2.1, and iOS surfaces no venue prompt anyway. This path cannot deliver "popup + validated network" for this product; the coexistence answer must come from another mechanism.

## Track C: alternatives on a validated network

RAW FINDINGS — TASK C: Discovery prompts on a VALIDATED (204-answering) hotspot

## Q1. Can a device trigger a "sign-in/website" style prompt on a validated network? YES — exactly one sanctioned mechanism: the Captive Portal API (RFC 8910/8908) with `captive: false` + `venue-info-url`

This is the headline finding: **Android 11+ fetches the Capport API via DHCP option 114 immediately after connecting, independent of probe results, and `venue-info-url` produces a user-visible notification even when there is no captivity at all.**

- Android 11 added support for DHCP option 114 (RFC 8910) pointing at an RFC 8908 JSON endpoint; devices "fetch the API contents immediately after connecting to the network." The system UI shows "a popup notice allowing users to visit the venue page" and an "Open site" button in the Network details screen. If the API is absent, Android falls back to the classic HTTP/HTTPS probes ([Android Developers: Captive portal API support](https://developer.android.com/about/versions/11/features/captive-portal), [Android Police coverage](https://www.androidpolice.com/2020/07/21/android-11-will-make-public-wi-fi-logins-easier-with-a-new-captive-portal-api/)).
- Confirmed WITHOUT any captive portal: a Dec 2025 write-up ([stevetech.me: Add 'Open Site' and 'Expires On' values to your WiFi network](https://stevetech.me/posts/wifi-captive-portal-api)) tested serving `{"captive": false, "venue-info-url": ..., "seconds-remaining": ...}` on a normal internet network ("without the whole captive portal setup, and it turns out it is [possible]"). Result on Android: (a) **"Android will also show a notification as a shortcut to the venue url"** on the home screen, (b) an "Open site" button in WiFi settings, (c) "1 day left" text under the network name from `seconds-remaining` (purely informational — device does not disconnect). Mikrotik config example given: `code=114 value="s'https://.../?...'"` with force=yes; also DHCPv6 option 103 / IPv6 RA option 37.
- Field report: "[Capport API - Venue Info URL works amazing on Android 12](https://community.ui.com/questions/Capport-API-Venue-Info-URL-works-amazing-on-Android-12/3b1fd283-d522-4dfc-b30c-6f97e85bd089)" (UniFi community; page is JS-walled but title/indexing confirms Android 12 behavior).
- The notification opens the URL in the REGULAR browser, not the captive mini-browser — an Apple forums poster describing Android's behavior: Android shows "an event notification... the ability to click that notification to open 'venue-info-url' in a regular browser" ([Apple Developer Forums thread 695574](https://developer.apple.com/forums/thread/695574)). This dodges the mini-browser/no-file-chooser problem entirely.

**The hard blocker: TLS.** RFC 8908: "The API server endpoint MUST be accessed over HTTP using an https URI" and user-portal-url/venue-info-url "MUST be accessed over TLS" ([RFC 8908](https://datatracker.ietf.org/doc/html/rfc8908)). The API server "MUST present a valid certificate on which the client can perform revocation checks." Apple's doc likewise: TLS mandatory ([Apple: How to modernize your captive network](https://developer.apple.com/news/?id=q78sq5rv)). stevetech.me: "served over only HTTPS, plain HTTP is not supported as per the RFC," plus required headers `Content-Type: application/captive+json` and `Cache-Control: private` or `no-store`. Vendor docs confirm the practical consequence: "the device must have a trusted certificate and a DNS name" ([LANCOM Public Spot Capport docs](https://www.lancom-systems.com/docs/LCOS/Refmanual/EN/topics/pspot_template-cp-api.html)); self-signed certs fail on offline/local networks ([Mikrotik forum RFC8910 thread](https://forum.mikrotik.com/t/rfc8910-captive-portal/155377), [ESP32 forum: option 114 not working on Android/iOS](https://esp32.com/viewtopic.php?t=42046) — bot-walled, but title matches the failure mode).
  - Theoretical workaround: wildcard DNS already points any hostname at 4.3.2.1, so the ESP32 could serve HTTPS for a real domain with an embedded publicly-trusted cert + private key (e.g., `setup.apollolighting.com`). Costs: ESP32 TLS server RAM, public certs now max ~398 days (dropping to 47 days by 2029 → forced OTA/renewal pipeline), shipping a private key in firmware is extractable and violates most CA subscriber agreements — risky but some commercial devices do it (e.g., Plex-style per-device certs). Revocation checking is soft-fail on Android in practice.
  - Graceful degradation: if the cert doesn't validate, Android silently ignores the Capport API and falls back to probes → 204 → validated network, no notification. Nothing breaks; you just lose the prompt.
- **iOS**: supports option 114 / DHCPv6 103 / RA 37 since iOS 14 ([Apple doc](https://developer.apple.com/news/?id=q78sq5rv)) but does NOT show a venue-info-url notification — an iOS 15.7 user confirms "no notification appears," unlike Android ([Apple forums 695574](https://developer.apple.com/forums/thread/695574)); at most a "Portal" row appears inside the Wi-Fi network's settings page ([Splash Networks Mikrotik capport writeup](https://blog.splashnetworks.co/captive-portal-api-and-venue-info-url-on-mikrotik/)). So this trick is Android-only for a popup-like effect — which is fine, because Android is the problem platform (iOS can keep getting a 302→CNA; the device can discriminate by probe Host header: `captive.apple.com` vs `connectivitycheck.gstatic.com`/`generate_204`).
- No other trigger exists on a validated network. A bait-and-switch (serve 204, then start failing probes to force the "sign in" notification) makes Android re-evaluate, mark WiFi unvalidated, and demote it from default network — recreating the original cellular-routing problem, so it is not coexistence.

## Q2. Wildcard DNS on a validated network: Chrome DOES use the WiFi DNS and lands on the device

- Once the 204 answers validate the hotspot, Android makes WiFi the default network even with mobile data on: "When the Wi-Fi network validates, the system prefers it to the mobile network, mainly because it is unmetered" ([AOSP: Network selection](https://source.android.com/docs/core/connect/network-selection), [NET_CAPABILITY_VALIDATED](https://developer.android.com/reference/android/net/NetworkCapabilities)). DNS is per-network (each network's `LinkProperties` carries its DNS servers), and apps resolve via the default network → the ESP32's wildcard DNS at 4.3.2.1 ([Android: Read network state](https://developer.android.com/develop/connectivity/network-ops/reading-network-state)). So with 204 + wildcard DNS, any typed hostname in Chrome resolves to 4.3.2.1 and reaches the device; mobile data being ON is irrelevant because cellular is no longer the default route.
- Caveats that gate "type any website":
  - **Private DNS (DoT)**: Android's default "Automatic" mode falls back to cleartext DNS when DoT:853 fails → still lands on the device. But **Strict mode** (user-entered hostname) refuses fallback; the hotspot can't satisfy it, giving "Private DNS server cannot be accessed" and the network won't validate at all — the entire 204 strategy degrades for those users ([PIA blog](https://www.privateinternetaccess.com/blog/private-dns-server-cannot-be-accessed/), [NordVPN](https://nordvpn.com/blog/private-dns-server-cannot-be-accessed/)).
  - **Chrome Secure DNS**: "Automatic" only upgrades to DoH for recognized providers; unknown ESP32 resolver → falls back to system DNS → device. 
  - **HTTPS-Upgrades**: typed bare domains are tried as https:// first; Chrome "will fall back to HTTP when the HTTPS attempt fails (including... certificate errors, such as name mismatch or untrusted self-signed certificate)" and allowlists the host ~7 days ([Chromium Intent to Ship: HTTPS Upgrades](https://groups.google.com/a/chromium.org/g/blink-dev/c/cAS525en8XE)). BUT **HSTS-preloaded domains (google.com, facebook.com, most big sites) hard-fail with a cert error and no fallback**. So "open google.com" will NOT work; a dedicated non-HSTS vanity hostname (printed on the box, e.g. `wled.setup`→ any real non-preloaded domain you own) or the literal IP `4.3.2.1` works reliably.
  - Side effect: while connected, the phone genuinely has no internet but believes it does — all apps route to the ESP32 and stall. Acceptable for a 2-minute setup flow, but it's user-visible weirdness.

## Q3. mDNS: nothing user-visible on join, on either OS

- mDNS/DNS-SD discovery is app-API only: Android `NsdManager`, iOS Bonjour with per-app local-network permission. No OS notification, prompt, or list entry appears merely because a device on the network advertises services ([Flutter NSD plugin docs summarizing both platforms](https://pub.dev/packages/flutter_nsd), [jaanus.com: Implementing Bonjour across iOS and Android](https://jaanus.com/implementing-bonjour-across-ios-and-android/)). Cast targets/AirPrint printers surface only inside the relevant app dialogs. 
- Secondary utility only: iOS Safari resolves `.local` names (Bonjour), so `http://wled.local` works on iOS; Android's stock resolver historically does not do mDNS for browsers — but this doesn't matter here because the wildcard DNS answers `wled.local` (or anything else) with 4.3.2.1 anyway. No prompt value.

## Q4. OS onboarding hooks without an installed app

- **Android Fast Pair**: BLE-advertisement-based; Play services shows a half-sheet ("device name, photo, Connect button") with no app installed, and since fall 2022 it extends to Matter smart-home commissioning ([Google Fast Pair docs](https://developers.google.com/nearby/fast-pair/specifications/introduction), [Android Authority overview](https://www.androidauthority.com/google-fast-pair-2-3220791/)). BUT: requires registering a Model ID in Google's Nearby Devices console + certification; the half-sheet drives BT pairing / companion-app install / Google Home Matter flow — it cannot open an arbitrary local URL. Also requires BLE advertising (WLED builds typically compile out BT to save RAM). Not usable as a web-setup popup.
- **Matter onboarding**: the Android half-sheet/Google Home path requires an actual certified Matter device (VID/PID in the DCL); WLED isn't Matter. Product pivot, not a hook.
- **iOS**: WAC/HomeKit Wi-Fi accessory setup ("Set up new device..." in Wi-Fi settings) requires the MFi program; Matter requires Home app + QR. Nothing certification-free exists ([Apple deployment docs](https://support.apple.com/guide/deployment/wi-fi-settings-dep168e876c9/web)).
- **Dead end**: Google Nearby Notifications (Physical Web / Eddystone-URL beacons → notification) was shut down Dec 2018.
- **NFC tag (viable, zero-certification)**: a passive NDEF URL tag in the device/packaging: iPhone XS+ background tag reading pops a notification that opens Safari; Android opens the URL directly. Encode `http://4.3.2.1` — works once the phone is on the (validated) hotspot. Costs an NFC sticker; no OS gatekeeping. (General platform behavior; not from a single citable page above.)

## Bottom line: CAN both coexist?

**Yes, on Android 11+ — via exactly one path: answer probes with 204 (validated network, real Chrome, WiFi as default route, wildcard DNS lands users on the device) AND advertise DHCP option 114 → Capport JSON `{"captive": false, "venue-info-url": "http(s)://…"}` → Android posts a tappable notification that opens the setup page in the full browser.** This is the only OS-blessed "popup on a working network" mechanism that exists. The single engineering obstacle is that the Capport API endpoint (and per RFC 8908, the venue URL too) MUST be HTTPS with a publicly-trusted cert — hard on an offline ESP32 (embedded real cert + renewal pipeline is the only route; self-signed silently no-ops). Failure mode is graceful: no cert → no notification, but the 204/wildcard-DNS flow still works, with printed fallback instruction "open 4.3.2.1" (IP literal — immune to HSTS/DNS caveats). iOS ignores venue-info-url, so serve iOS probes (`captive.apple.com` Host header) a 302→CNA instead — per-OS discrimination on one hotspot is straightforward since Android and Apple probe different hostnames. Whether current Android builds enforce the https scheme on the venue-info-url value itself (vs just the API endpoint) is the one point the sources don't settle — needs a 30-minute empirical test with option 114 + an https API returning an `http://4.3.2.1` venue URL.
