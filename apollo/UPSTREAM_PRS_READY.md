## PR 1: WiFi sleep setting is never applied on the AP-only path

Branch: fix/ap-mode-wifi-sleep (cut from upstream/main)
Fork commit: 2aaecdd1, take ONLY the wled00/wled.cpp hunk (the commit also
carries the FX.cpp force-scroll change and apollo/fs files; exclude all of
that). Trim the fork's long inline comment to one short clause.

### Title

    AP mode: apply the WiFi sleep setting (factory-fresh units keep modem power-save on the setup AP)

### Body

```markdown
### What this fixes
`WiFi.setSleep(!noWifiSleep)` is only called inside `initConnection()`'s
`WLED_WIFI_CONFIGURED` branch (wled00/wled.cpp:799 at v16.0.1, the only
applicable setSleep call in the tree). A factory-fresh unit, or any unit
running AP-only, never reaches it, so the Arduino core default (modem
power-save enabled; the vendored core sets WIFI_PS_MIN_MODEM on ESP32-S3)
stays active while the device serves its setup AP. A configured unit that
brings the AP up alongside STA does get the call; it is specifically the
unconfigured/AP-only path that misses it, which is exactly the out-of-box
moment.

WLED's own intent is the opposite: `noWifiSleep` defaults to true on ESP32
("disabling modem sleep modes will increase heat output and power usage, but
may help with connection issues"), but that intended default never takes
effect for a brand-new device on its setup hotspot.

### The change
One line in `WLED::initAP()`, inside the existing `#ifdef ARDUINO_ARCH_ESP32`
block, right after the existing `WiFi.setTxPower(...)` call:

    WiFi.setSleep(!noWifiSleep);

It mirrors the configured-STA path exactly and honors the user's setting in
both directions: a user who deliberately enabled WiFi sleep now gets it in AP
mode too, instead of getting the core default by accident.

### Testing
Root cause established from source (the setSleep call is unreachable on
unconfigured units; core default is power-save on). On hardware (ESP32-S3
16MB opi, HUB75 product, factory-fresh unit serving its setup AP): with this
change plus a product-side TX power fix applied together, the AP measured
0% loss with single-digit-ms average RTT while the full web UI and JSON API
were exercised over it. We did not isolate an A/B latency delta for this
line alone (the softAP-only power-save penalty is workload and client
dependent); the honest case for this patch is consistency: the existing
setting should apply on every radio path, and today it silently does not.

### Risk / compatibility
- ESP32 family only; the line sits inside the existing ARDUINO_ARCH_ESP32
  guard. ESP8266 AP behavior unchanged (its `wifi_set_sleep_type()` call at
  wled.cpp:802 has the same STA-only asymmetry and could get the same
  treatment in a follow-up if wanted).
- With the ESP32 default (noWifiSleep = true) this slightly raises power
  draw and heat in AP mode, the same trade WLED already makes on the STA
  path.
- Users who enabled "WiFi sleep" in settings keep sleep enabled in AP mode
  too.
```

### Exact hunk (v16.0.1 numbering)

wled00/wled.cpp, `void WLED::initAP(bool resetAP)` (starts line 644), hunk
`@@ -657,6 +657,7 @@`, one added line after `WiFi.setTxPower(...)` inside the
existing `#ifdef ARDUINO_ARCH_ESP32` block.

### Expected review questions

- "Does modem power-save actually degrade a softAP-only interface?" It is
  contested territory (ESP-IDF documents modem sleep as a station-mode
  feature). Answer with the consistency framing, not a latency promise.
- ESP8266 analog in the same PR: be ready to add it or scope it out.

## PR 2: Scrolling Text cannot scroll horizontally when the text fits

Branch: fix/scrolling-text-force-scroll (cut from upstream/main)
Fork commits: 2aaecdd1 (2 lines of FX.cpp; exclude everything else in that
commit) + c4c6c2f9 (1 line). Submit the combined net diff, 3 changed lines.

### Title

    Scrolling Text: let the Reverse checkmark force horizontal scrolling for text that fits the segment

### Body

```markdown
### What this fixes
`mode_2Dscrollingtext()` only scrolls horizontally when
`totalTextWidth > cols`. Text that fits is centered and held (or scrolled
vertically at intensity 0/255). There is no way to make fitting text scroll
horizontally: check3 ("Reverse") is only evaluated inside the overflow
branch, so for fitting text it is dead code (verified: the only check3 use
in the function is the reverse-direction branch inside the overflow path).

Real-world case: a short word on a 64px-wide panel just sits there
("APOLLO M-1" is 58px in the default 6x8 console font, 56px in the 5x12 font
at max Font size; either way it fits and holds). Users who chose an effect
called Scrolling Text expect an option to make it scroll.

### The change
Three lines in `mode_2Dscrollingtext()`. Check3 now also forces horizontal
scrolling when the text fits:
- the fits-vertically branch is skipped when check3 is set;
- the scroll-step condition becomes `totalTextWidth > cols || SEGMENT.check3`;
- forced scrolling of fitting text always travels right-to-left (ticker
  reading direction); check3's reverse meaning applies unchanged to
  overflowing text.

### Testing
On hardware (ESP32-S3, 64x64 HUB75, v16.0.1 base):
- "APOLLO M-1" (fits): static without check3 (unchanged); with check3 it
  scrolls continuously right-to-left. Verified on glass.
- Overflowing text: unchanged without check3; with check3 still scrolls
  reversed, as today.
- Vertical scroll via intensity 0/255 for fitting text: unchanged when
  check3 is off.

### Risk / compatibility
- No change unless check3 is set on fitting text, a previously dead
  combination.
- Behavior change for that combination: previously centered hold (or
  vertical scroll at intensity 0/255), now horizontal scroll. We believe
  checking the box expresses exactly that intent, but it is a change.
- Known interaction: with check3 set and intensity at 0 or 255, the yoffset
  mapping still applies, so the forced horizontal scroll runs pinned at the
  segment's top or bottom edge rather than centered. That matches the
  intensity slider's Y Offset meaning, but reviewers testing ix=0/255 will
  see it; happy to clamp the offset for forced scroll if preferred.
- The checkmark keeps its "Reverse" label and now does double duty. If
  maintainers prefer a fourth checkmark ("Force scroll") over overloading,
  happy to adjust; overloading costs zero UI/state space, a new checkmark
  is cleaner semantics but touches effect metadata.
```

## PR 3: JSON effect change leaves a frozen segment frozen (live-paint black-screen trap)

Branch: fix/fx-change-thaws-freeze (cut from upstream/main)
Fork commit: dcdacb45, take ONLY the wled00/json.cpp hunk (the commit also
touches fork docs). Trim the fork's inline comment.

### Title

    JSON API: changing the effect thaws a frozen segment unless the same message sets frz

### Body

```markdown
### What this fixes
The per-pixel JSON API ("i" arrays, used by live-paint tools) intentionally
sets `seg.freeze = true` (json.cpp:323-324) so effects do not repaint the
drawing. But the effect-selection flow never thaws: picking a new effect in
the stock UI sends `{"seg":{"fx":N,...}}` with no frz key (index.js:2448),
`seg.setMode()` does not touch freeze, and frozen segments skip their effect
function entirely (FX_fcn.cpp:1344). The user sees the frozen canvas, and if
they cleared their drawing first, a black panel, with the newly selected
effect name highlighted in the UI.

Escapes exist but none of them live in the flow the user is actually in:
the per-segment (un)Freeze icon (easy to miss and cryptic to a newcomer),
power off/on (FX_fcn.cpp:1803 and json.cpp:389 both unfreeze), or a client
sending "frz":false explicitly. From within the effect picker itself there
is no way out, which makes the selected-but-not-running state read as a
device bug.

Reproduced flow: paint pixels via "i", clear, then pick any effect in the
stock web UI. Result: black screen with the effect apparently selected.

### The change
In `deserializeSegment()` (wled00/json.cpp): when an "fx" value actually
changes the mode, clear `seg.freeze` unless the same JSON message carries an
explicit "frz" key. "frz" is parsed earlier in the same function (line 201),
so an explicit key keeps full control: `{"fx":X,"frz":true}` changes the
effect AND stays frozen, exactly as before.

Rationale: picking an effect is the user saying "run this". Precedent for
implicit thawing exists in the same file: turning the light on from off
clears freeze on all segments (json.cpp:389-391, with the documented
realtime-mode exception right below it).

### Testing
On hardware (ESP32-S3, 64x64 HUB75, v16.0.1 base), live over the JSON API:
paint via "i" -> frz reports true; clear -> still true; pick an effect in
the stock UI -> effect runs and frz reports false (previously: black
screen). A client that manages freeze explicitly (sends frz in the same
message) behaves identically before and after. Re-sending the same fx value
does not thaw (the guard is inside the existing `fx != seg.mode` branch).
The paint tool used was a live-paint page driving the stock "i" API; the
freeze mechanism being patched is stock WLED.

### Risk / compatibility (small API semantics change, please read)
- Any JSON client that changes fx WITHOUT a frz key on a frozen segment now
  gets a running effect instead of a frozen canvas. We believe that is what
  the stock UI and virtually every client intend, but a client relying on
  "set the mode now, stay frozen, thaw later" changes behavior; the escape
  is explicit and cheap: include "frz":true in the same message.
- Presets and playlists flow through deserializeSegment(), so a preset that
  changes fx and omits frz now thaws. Narrower than it sounds: presets saved
  from the UI ALWAYS store frz (serializeSegment emits it unconditionally,
  json.cpp:592), so only hand-authored or API-crafted presets that omit frz
  are affected, and under the old behavior those presets appeared to do
  nothing on a frozen segment.
- Scope: this covers the JSON API only. Effect changes via the HTTP API
  (set.cpp, FX=) and UDP sync (udp.cpp setMode calls) do not pass through
  deserializeSegment and still leave segments frozen. We kept the fix
  minimal and JSON-side because that is where the stock UI and live-paint
  clients live; if maintainers prefer the thaw inside Segment::setMode() so
  every path behaves the same, we are happy to rework it that way.
- Residual trap either way: re-selecting the already-active effect is a
  no-op (fx does not change), so that click still does not thaw.
- No change when fx is absent, when fx does not change the mode, or when
  the message carries any frz key.
```
